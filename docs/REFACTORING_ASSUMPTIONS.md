# 重构假设说明

## 1. 为什么选择异步事件驱动，而不是继续同步处理

同步链路把“解析 → 规则 → 校验 → 逐行写库”放在一次 HTTP 请求里：

- Vercel Serverless 有执行时间上限，10,000 行在 30 分钟内也完成不了；
- 多个大文件并发上传会瞬间打满数据库连接池；
- 用户只能看到 loading，无法感知进度和失败位置；
- 日志只有 `insert failed`，无法定位到具体行和字段。

异步事件驱动把请求边界与处理边界分离：上传只负责“收文件、建任务、写 Outbox、返回 task_id”，后续由队列 Worker 分片处理。这样上传响应可控（P95 < 1s），处理可以水平扩展，失败可以通过任务/批次/行三级模型精确定位。

## 2. 处理单元大小如何设计

默认 1000 行/批，理由：

- 每批 1000 行的 SKU `IN` 查询和批量 UPSERT 都在 PostgreSQL 参数与事务的舒适区间内；
- 单个处理单元失败时重试成本约 1 秒，不会重放太多数据；
- 批次数量（10 批）便于看板和日志呈现；
- 流式读取按“文件前缀 + 数据行切片”，单批内存仅一个批次的行数据，不会把 10,000 行全部载入。

处理单元大小可通过 `BATCH_SIZE` 调整；增大批次会减少 SQL 次数但提高单次失败成本，减小批次会提高并发度但增加调度开销。

## 3. Worker / Consumer 容量规划

- 本地/单机 Worker：`WORKER_CONCURRENCY=4`，实测 10,000 行约 3.3s；
- 每批平均总耗时约 1s，4 并发下 10 批约 2.5 轮 ≈ 3s；
- 若吞吐目标提升到 50,000 行/分钟，可将 Worker 扩展到 3~5 个实例（各自 4 并发），或提高单 Worker 并发到 8~10；
- BullMQ 支持多 Worker 消费同一队列，天然水平扩展。

## 4. 10,000 单/分钟性能推导

实测数据（见压测报告）：

| 阶段 | P50 | P95 |
|---|---:|---:|
| parse（流式读取） | 749ms | 1221ms |
| rule（V2 规则引擎） | 13ms | 28ms |
| validate（SKU + 重复键批量查询） | 25ms | 41ms |
| insert（批量 UPSERT + 错误写入） | 215ms | 392ms |
| total | 982ms | ~1300ms |

单批 1000 行约 1s，4 并发 = 4,000 行/s 的理论峰值（实际约 3,000 行/s）；10,000 行约 3.3s，远低于 60s 红线。数据库连接峰值 = Worker 并发 × 单批连接数（单批 1 个连接池连接复用），连接池上限 10，不会打满。

## 5. 数据库连接池与 Worker 并发如何控制

- `DATABASE_POOL_SIZE` 控制 postgres.js 连接池上限（默认 10）；
- `WORKER_CONCURRENCY` 控制单进程并发批次数（默认 4），因此峰值连接数 ≤ 10 且共享同一连接池；
- 所有查询都是批量 SQL（1 次 IN 查询、1 次批量 UPSERT），不存在逐行 SQL 放大连接占用；
- 通过 `batch_performance_log.validate_duration_ms / insert_duration_ms` 可以持续观测连接池是否成为瓶颈。

## 6. Outbox 如何避免“任务创建成功但消息丢失”

- 任务、批次、Outbox 事件在**同一个数据库事务**写入；
- Dispatcher 用 `FOR UPDATE SKIP LOCKED` 轮询，投递成功才标记 `sent`；
- 投递失败记录 `retry_count` 与 `next_retry_at` 指数退避；
- 若“入队成功但未标记 sent”时宕机，BullMQ 的确定性 `jobId` 保证重复入队不产生重复 Job；
- Sweeper 额外扫描“任务 pending 但 Outbox 缺失”的场景并重建事件，作为最后一层保险。

## 7. 处理单元 Job 如何做到幂等

三层幂等：

1. **队列层**：`jobId = task_id-unit_id`，同一处理单元不会重复入队；
2. **状态层**：Worker 条件 UPDATE `status IN (pending, retry) -> processing` 抢占，重复消费抢占失败直接返回；
3. **数据层**：`waybills` 业务唯一键 `external_order_no + sku_code + line_no`，`ON CONFLICT DO UPDATE` 保证不产生重复行；进度累计使用原子 SQL 而不是读改写。

## 8. 部分行失败时为什么允许成功行继续入库

批量导入的业务语义是“尽最大努力处理文件”：

- 一行失败（如 SKU 不存在）不应阻塞另外 9,999 行；
- 成功行入库后，用户只修失败行即可，无需整单重传；
- 失败行全部写入 `import_task_errors`，可导出、可筛选、可修复后重新导入；
- 任务终态为 `partial_success`，前端和监控都明确展示成功/失败数量，不存在“静默部分成功”。

## 9. SKU 校验降级的触发条件和风险提示

触发条件：

- `sku_master` 查询超过 `SKU_CHECK_TIMEOUT_MS`（默认 3s）；
- 数据库连接短暂失败（ECONN / connect / timeout）。

降级行为：

- 任务写入 `degraded=true` + `degraded_at`；
- 当前及后续批次跳过 SKU 主数据校验，仅做必填/电话/数量/重复等本地校验；
- 批次记录 `sku_validation_skipped=true`，任务累计 `degraded_rows`；
- 前端任务详情页显示“⚠️ SKU 校验已降级：本次导入未经过商品主数据完整校验，数据可能需要后续复核”；
- 服务恢复后新任务自动恢复正常校验（降级状态按任务隔离，不全局关闭）。

后续补校验策略：当前版本将降级任务标记为需复核，由运维导出 `degraded_rows` 对应的批次行范围人工复核；不自动补跑，避免与已入库数据产生重复/冲突。

## 10. 错误日志中敏感数据如何脱敏

- 手机号存储前脱敏为 `138****5678`；
- 地址存储前保留前 6 字符和后 4 字符，中间以 `***` 替代；
- 所有 API 输出再次调用 `maskSensitiveValue`，即使存储层未来变化也不会泄露；
- 错误明细支持导出 CSV，导出的同样是脱敏值；
- 字段级脱敏规则集中在 `src/lib/errors.ts`，便于审计与调整。

## 11. 压测数据如何生成、如何清理

生成：

```bash
npm run seed
```

写入 20,000 条 SKU（`SKU_00001` ~ `SKU_20000`），生成 10,000 行 `test-data/10000-orders.xlsx`，其中故意混入：

- 30 行非法 SKU（`SKU_90001+`）；
- 20 行坏手机号（`123`）；
- 20 行负数量；
- 10 行重复外部单号。

清理：

```bash
npm run seed:clean
```

删除压测任务关联的 waybills / errors / perf / trace / outbox / batches / tasks，并重建 SKU 主数据与压测文件。脚本可重复执行，不会造成脏数据不可控增长。

生产环境的 `import_task_errors`、`batch_performance_log`、`trace_events` 建议按 `created_at` 定期归档（例如每月归档到冷存储），`event_outbox` 已投递记录超过 30 天归档删除。

## 反思题（不计分）

### 1. 为什么不能继续同步，什么时候同步更简单可靠

同步适合“小文件、低频、单机、强一致、失败即整体回滚”的场景；大促 10,000 行/分钟下，同步的请求时长、连接池、可观测性都无法满足。异步把吞吐与延迟解耦，用 Outbox + 幂等换取可靠。

### 2. 处理单元变大/变小的影响

变大：SQL 次数少、吞吐高，但单批失败重试成本高、内存占用大；变小：并发粒度细、失败影响小，但调度与 SQL 次数增多，可能成为瓶颈。

### 3. 50,000 行/分钟时先成为瓶颈的是谁

大概率是数据库写入（UPSERT 的 WAL/IO）和连接池；Redis 队列在单机 5 万/分钟仍是毫秒级。扩展方向：读写分离/分库分表、COPY 批量装载、临时表合并、增加 Worker 与连接池上限。

### 4. 为什么业务幂等比消息只投递一次更重要

分布式系统无法保证“恰好一次”投递；只要消费者幂等（唯一键 + 状态机 + 原子累计），重复投递是无害的，比依赖昂贵且脆弱的 exactly-once 基础设施更可靠。

### 5. 部分失败应整体回滚还是成功行先入库

批量导入场景选择成功行先入库：失败定位成本低、用户修复成本低、符合大促吞吐目标；强一致场景（如财务）才需要整体回滚。

### 6. 原始值 vs 数据安全如何平衡

保留排障所需的结构（字段、行号、错误码），敏感字段存储与展示均脱敏；必要时将完整原文加密存储并做权限审计，而不是明文落库。

### 7. Outbox 表千万级如何清理

按 `created_at` 分区，已投递记录定期归档到冷表/对象存储；索引使用 `(status, next_retry_at)` 覆盖活跃投递，归档时批量删除或 DROP PARTITION，避免长事务。

### 8. 如何快速发现是规则问题而不是数据库问题

监控看板按阶段拆分 P50/P95/P99：若 `rule_duration_ms` 突增或 `E006` 错误占比上升，则是规则引擎/字段映射问题；若 `insert_duration_ms` 突增，则是数据库问题。Trace 时间线按批次展示各阶段耗时，可直接定位到具体规则与文件。
